# Le Voyage — R9E1 : récupération d'invitation sur un autre appareil

**Base vérifiée :** R9E0 `3db11330ba38de18c9d551135e0b335b24ca0574`. Branche de reprise `work/r9e1-cross-device-invitation`. Aucun déploiement Firebase ou merge main.

## Problème produit

La connexion e-mail de R9D9 conservait l'invitation dans le stockage local du premier navigateur. Sur un autre téléphone/ordinateur, le lien Firebase prouvait l'adresse mais ne rétablissait pas l'invitation. L'employé sans espace était légitimement refusé, sans parcours guidé permettant de compléter les deux preuves sur le même appareil.

## Correctif

- Sur l'écran de validation du lien e-mail, un champ facultatif permet de coller le **lien personnel d'invitation à l'équipe**. Il n'est pas envoyé à Firebase lors de `signInWithEmailLink` ; uniquement au serveur du Voyage avec le jeton d'identité Firebase.
- Le lien collé est validé avant l'échange du code Firebase : fragment hexadécimal de 64 caractères, chemin `/invitation.html`, même origine que le Voyage et aucune query. Les tokens bruts sont également acceptés. La vérification décisive reste l'autorisation serveur par UID et invitation, issue de R9D7.
- Sans saisie, le comportement sur le premier appareil reste inchangé (jeton d'invitation temporaire en local, puis suppression après connexion réussie).
- Après acceptation de l'invitation, le lien « Se reconnecter par e-mail » ferme la session de préinscription par l'API avec CSRF, avant de proposer la connexion normale. Aucun espace n'est accessible sous une session d'invitation provisoire.
- En cas d'échec de vérification, les messages ne révèlent pas de détails concernant les comptes existants.

## Tests

Nouveau scénario navigateur `tests/firebase-browser/email-link-recovery.spec.mjs` :
- second appareil avec lien complet de même origine → jeton Firebase et invitation transmis ensemble à l'API attendue ;
- origine étrangère ou chemin contenant une query → rejet dans le navigateur avant d'utiliser le code Firebase.

**Limites explicites :** il s'agit de tests avec Firebase SDK simulé et routes API simulées pour l'interface, en complément du test émulateurs R9E0. Aucune preuve de livraison d'e-mail par Firebase réel, aucun compte réel, aucun fournisseur distant activé et aucun déploiement de production.

## À valider avant pilote

Le R9E0 doit être vert pour la recette Auth/Firestore. Vérifier ensuite la boucle e-mail sur Firebase isolé (fournisseur autorisé par un opérateur), y compris le délai d'expiration, le lien ouvert dans un autre navigateur, la non-fusion des comptes Google/e-mail par adresse seule et la révocation d'accès.
