# V5 R9C2 — Formulaire de connexion des comptes habilités

29 octobre 2026. Parent : `238f700c149b89cca5d17452d2b83e7ed1288456`. Branche `work/v2-phase1-engine`, PR #1.

Le mode provisionné propose désormais une connexion e-mail/mot de passe dans la page existante. Les profils fictifs y sont masqués. Les identifiants sont transmis au service Firebase Authentication côté serveur ; ils ne sont ni conservés ni journalisés par cette implémentation. L’identité vérifiée et les droits préexistants restent obligatoires. Après succès, le navigateur rejoint le sélecteur d’espaces. Après échec, un message générique apparaît, le mot de passe est effacé et le bouton redevient utilisable. Aucun écran de création de compte ou de réinitialisation n’est livré.

`RC_AUTHENTICATION_MODE=provisioned` raccorde explicitement ce mode au lancement isolé. La configuration conserve le contrôle du projet test, des origines HTTPS et la protection Basic extérieure. Le gate Google de démonstration est refusé dans ce mode, car il gère une session et des profils fictifs distincts. En l’absence du paramètre, le mode de démonstration existant reste celui utilisé. Aucun paramètre distant n’est modifié.

## Fichiers

- `src/server/firebase-http.mjs` : configuration publique minimale et connexion par mot de passe, délai réseau de dix secondes, vérifications R9C1 et création de session chiffrée.
- `src/server/staging-config.mjs`, `scripts/serve-staging.mjs` : choix explicite du mode isolé.
- `src/web/login.ts`, `web/connexion.html`, `web/styles.css` : formulaire accessible et états de connexion.
- Tests de configuration, test HTTP sur Auth/Firestore émulés et parcours navigateur desktop/mobile ajoutés.

## Validation locale

Typecheck et build réussis. Les 20 tests d’accès existants passent ; le nouveau test de configuration passe également (21 tests d’accès distincts). Test HTTP du mode provisionné : 1/1, incluant mauvais mot de passe, connexion réussie, sélection et révocation.

Les quatre parcours navigateur ciblés (connexion historique et nouveau formulaire, desktop/mobile) n’ont pas pu démarrer localement : Chromium attendu absent et téléchargement retournant une archive invalide. Aucune capture ni validation visuelle revendiquée. Le parcours ajouté simule les réponses de connexion pour vérifier les états de l’interface ; il ne prétend pas effectuer une connexion réelle. La CI utilise son installation Chromium habituelle et doit confirmer ces parcours.
