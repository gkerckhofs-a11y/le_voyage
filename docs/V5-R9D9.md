# V5 R9D9 — Préparation contrôlée des connexions par lien e-mail

Base : R9D8 `dfda9730ccac2fa0551fcc2cdf4a6863fdf7b62e`, après PR #3. Tous les collaborateurs possèdent un e-mail. Objectif produit : lien personnel d'invitation, connexion e-mail sans mot de passe, acceptation d'équipe, puis espace autorisé.

## Livré : première étape de sécurité

`src/server/email-link-preparation.mjs` fournit un service d'**aperçu opérateur exclusivement**, qui contrôle qu'une identité Firebase Auth préexistante est active, avec e-mail vérifié, et que l'invitation est en attente, non expirée et adressée exactement au même UID. Le service produit les paramètres de redirection Firebase (URL HTTPS canonique sur le domaine de l'application ; `handleCodeInApp:true`). Il ne contient pas le jeton de l'invitation dans l'URL de redirection. Aucune invitation n'est créée et aucune permission n'est accordée par ce service.

Cette étape n'expose **aucun endpoint public**, n'envoie **aucun courriel**, n'appelle **aucun fournisseur distant**. Aucun compte Google distant, ni projet Firebase réel n'a été modifié.

## Reste à réaliser avant utilisation réelle

1. Valider le domaine autorisé et activer le fournisseur Email/Password et l'option Email link dans Firebase Authentication du **projet isolé** uniquement, avec autorisation explicite ; tester le code Firebase réellement délivré.
2. Fournir une interface ou procédure de remise d'invitations : destinataire connu, demande explicitement autorisée, limitation de fréquence, réponses génériques et journal d'audit. L'envoi doit utiliser un fournisseur e-mail configuré ; le présent module ne le fait pas.
3. Faire aboutir sur le même navigateur ou un autre appareil : preuve de propriété de l'e-mail **et** lien d'invitation distinct. Un fragment d'invitation en `sessionStorage` n'est pas portable entre appareils. Prévoir un canal de reprise sûr sans divulguer le jeton d'invitation dans des logs ni dans un lien public.
4. Échanger l'ID token Firebase email-link vérifié avec `/api/auth/identity` et son `invitationToken` (R9D7) ; les sessions restent restreintes à l'invitation et les rôles sont créés exclusivement au moment de l'acceptation.
5. Conserver Google pour les comptes qui le préfèrent. Une correspondance de courriel ne fusionne jamais automatiquement des UID différents.
6. Contrôler les tests end-to-end sur Auth et Firestore émulés, puis sur staging isolé ; aucun déploiement production, aucune migration, aucune fusion dans `main` sans accord.

**Statut :** fondation sécurisée, parcours par e-mail **non encore opérationnel**. Ne pas vendre comme activé ni activer silencieusement sur le serveur de test.
