# V5 R9D6 — Sessions Google partagées et chiffrées

29 octobre 2026. Parent `5ee1a1617758c674bf2e1de1b574775c5c035539`, branche `work/v2-phase1-engine`, PR #1.

## Résultat

Le gate Google provisionné exige désormais un stockage de session explicite. Le lancement isolé lui fournit le stockage Firestore chiffré R9B, avec la même clé durable de staging. Les états préconnexion (10 minutes), la session Google vérifiée et le lien vers la session applicative sont conservés chiffrés. Les documents sont distingués par un type dans le contenu chiffré ; un jeton applicatif présenté comme cookie extérieur ne permet pas d’ouvrir le gate.

Le passage de l’état préconnexion à l’état connecté vérifie la version attendue dans la transaction de création. Deux échanges concurrents ne peuvent pas utiliser la même session préalable avec succès. La durée finale demeure limitée à l’expiration applicative, au plus 55 minutes. Les requêtes suivantes relisent l’état partagé et revérifient la session Google/UID/liste des testeurs ; aucun cache mémoire de remplacement n’est utilisé en mode provisionné.

Le proxy attend désormais le résultat applicatif avant de traiter un nouveau cookie : la rotation de l’espace est enregistrée dans le gate partagé avant la réponse, sans exposer le jeton intérieur au navigateur. La déconnexion retire les états concernés ; un logout applicatif déjà expiré retire également le gate. Les conflits de versions sont refusés, sans recréer de session supprimée. Une opération ayant subi un conflit peut nécessiter reconnexion ; aucune reprise automatique qui écraserait un état plus récent n’est ajoutée.

Le mode de démonstration historique conserve son registre mémoire et sa durée distincte. Les sessions expirées du gate provisionné utilisent la même enveloppe `expires/version` que les sessions applicatives et sont donc couvertes par l’outil manuel de nettoyage R9C9. La création de nouveaux états Google préconnexion est refusée à partir de 1 000 documents de session actifs dans ce stockage partagé : limite conservatrice du staging, pas un engagement de capacité commerciale.

## Validation

**13/13 tests locaux** gate/configuration, **6/6 tests émulateurs** incluant persistance Google, stockage applicatif et nettoyage. Soit dix-neuf cas distincts, sans recompter les répétitions. Typecheck et diff réussis.

Le scénario dédié crée deux gates et un troisième objet de remplacement sur le même Firestore émulé. Il vérifie : état préconnexion lu sur une autre instance, connexion, refus du cookie intérieur, rotation applicative visible entre instances, lecture depuis le remplacement, absence de secrets en clair dans les documents, déconnexion partagée et concurrence de promotion avec un seul succès. Le fournisseur Google et sa session signée sont simulés ; le stockage, les transactions, le chiffrement et les échanges HTTP du gate sont réels sur émulateur. Il ne s’agit pas d’un OAuth Google ni d’un redémarrage de service Cloud distant.

Aucun écran ou asset navigateur modifié, aucune nouvelle capture. Le scénario spécifique est rejoué après le garde-fou de capacité. Les tests de régression de session couvrent également remplacement du processus applicatif et révocation. La CI complète du nouveau commit reste à suivre.

## Suite et limites

Cette tranche remplace la limite mémoire décrite dans R9D5 pour le mode provisionné. La clé de chiffrement doit être stable et identique entre instances du staging ; sa rotation invalide les connexions existantes. Configuration réelle Google, comptes habilités et recette distante multi-instance restent à valider avant pilote. Les nouveaux comptes sans espace continuent à utiliser le parcours d’invitation distinct ; aucun élargissement de rôle ou de liste autorisée.

Aucune donnée distante, suppression, déploiement, migration production ou fusion main. À la reprise : accès/moteur du parent verts, carte/intégration en cours.
