# V5 R9E0 — Recette authentification e-mail avec invitation (émulateurs)

Base : PR #4, branche `work/r9d9-email-link-staging`, commit `aeb460f5b06535b0d0e7403ff77d8dc7988c62ed`. Ce travail ne modifie ni `main`, ni Firebase distant.

## Portée

L'interface de connexion par e-mail existe déjà en R9D9 (opt-in, staging isolé). Cette tranche ajoute une **recette intégrée** des éléments serveur avec les émulateurs Firebase Authentication et Firestore :

1. Préparer deux comptes fictifs et une invitation nominative.
2. Demander un code d'accès e-mail Firebase via le protocole REST **émulé**, sans envoyer d'e-mail.
3. Lire le code OOB du simulateur local (jamais l'enregistrer dans le dépôt ou les logs).
4. Échanger le code contre une identité Firebase, puis vérifier que l'UID est celui du destinataire initial.
5. Vérifier que l'identité sans invitation ne donne aucun accès ; avec invitation, seule la page d'acceptation est permise.
6. Accepter l'invitation, puis ouvrir l'équipe grâce à une nouvelle session, sans accès aux budgets directeur ou au cockpit cadeaux.

## Tests

`firebase emulators:exec --project demo-rc-voyage --config firebase/emulators.json --only auth,firestore "node --test tests/firebase/email-link-flow.test.mjs"`

La CI Firebase intégrée du dépôt exécute tous les tests `tests/firebase/*.test.mjs` et la suite Playwright. Une recette avec Firebase distant ou un fournisseur de messagerie reste **non réalisée** ; aucun compte réel n'est créé et aucun e-mail n'est transmis.

## Limites

Le scénario exige un compte Firebase préexistant et l'unicité de l'identifiant ; ne jamais fusionner automatiquement les identités par adresse. L'envoi des invitations aux employés n'est pas encore géré dans l'application. Le parcours multi-appareils reste à finaliser : il ne suffit pas de récupérer l'adresse depuis le lien Firebase pour attribuer une équipe sans vérifier l'invitation séparément.

Aucun déploiement, activation de fournisseur Auth, fusion de branche ou changement de données réelles.
