# Le Voyage — R9E2 : envoi contrôlé des invitations (transport désactivé)

**Source :** branche R9E1 `work/r9e1-cross-device-invitation` au commit `8265adf53bddc7f0d77e75d36b58c0abe21d7acd`. Nouvelle branche de travail `work/r9e2-invitation-delivery`. Pas de déploiement Firebase, ni fusion de `main`.

## Fonctionnel

L'organisateur peut créer une invitation et en copier le lien (mode existant) ; une action distincte « Envoyer une invitation par e-mail » est désormais prévue. Cette action **n'est visible** que si un transport e-mail serveur a été explicitement injecté et autorisé sur l'environnement de test isolé. Aucun transport n'est configuré dans le serveur de staging actuel.

L'envoi cible **exclusivement l'adresse vérifiée du compte Auth correspondant à l'UID destinataire**. Le navigateur ne peut pas choisir l'adresse d'envoi, le contenu ou une URL arbitraire. Le serveur doit revérifier le droit `canInvite` pour la campagne et le destinataire avant la création et la transmission de l'invitation. La connexion ultérieure reste liée à l'UID de l'invité, pas seulement à l'adresse.

## Protections

- Couche serveur `createInvitationDelivery`, accessible uniquement par `/api/invitation/send` en mode provisionné et sous rôle actif organisateur, avec session et CSRF.
- **Désactivée par défaut** : nécessite explicitement `invitationEmailTransport.send`, une origine HTTPS canonique et un projet Firebase isolé. Pas de service SMTP, API e-mail, clé ni nouveau domaine inventé.
- Réservation Firestore par destinataire : garde de 10 minutes contre les envois répétés ; identifiant d'opération durable pour interdire les renvois sur un rejeu, même concurrent.
- Journal minimal : statut `preparing / sending / sent / review`, destinataire UID, référence d'invitation et dates. **Aucun contenu d'e-mail ni jeton secret** conservé dans cette projection.
- Après une erreur de transmission, tentative de révocation de l'invitation et statut `review` ; aucune répétition automatique. Si l'envoi a réussi mais que la confirmation en base échoue, l'état doit être vérifié manuellement.
- L'API ne renvoie **jamais le lien secret** de l'invitation dans le résultat `send`. Le lien n'est construit que dans le service de transport autorisé.

## Validation

Nouveau test `tests/firebase/invitation-delivery.test.mjs` : habilitation, compte actif/vérifié, destinataire imposé, exclusion des doublons, cooldown persistant, retrait en cas d'erreur et état de revue. Le transport est simulé ; aucun e-mail réel n'est envoyé.

Commandes ciblées :

```bash
firebase emulators:exec --project demo-rc-voyage --config firebase/emulators.json --only auth,firestore "node --test tests/firebase/invitation-delivery.test.mjs"
npm run typecheck
npm run build:web
```

## Non inclus / décisions de mise en service

Cette tranche n'active aucun provider réel. Avant toute utilisation, choisir le fournisseur d'envoi et valider DNS d'envoi, secrets et quotas, politiques anti-abus, limitations de destination, protection contre l'usurpation, journal des délivrances et recette réelle sur des comptes testeurs consentants. Puis configurer explicitement le transport du staging et réaliser un pilote. Aucun message n'a été envoyé, aucun compte réel modifié et `main` demeure intacte.

**Attention :** les comptes Firebase destinataires doivent encore exister pour que l'organisateur puisse les inviter ; la création automatique d'un compte Auth à partir d'une simple adresse n'est pas couverte ici.
