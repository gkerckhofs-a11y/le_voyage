27 octobre 2026. Reprise du HEAD réel `26233a0045e760a77827aba62f9469b83deee48f`. CI Firebase et moteur réussies ; les relances documentaires accès/cartes étaient encore en file. Branche `work/v2-phase1-engine`, PR 1. Suite du raccordement V3-D2, sans modification du moteur.

## Réalisation

- `src/server/firebase-http.mjs` branche les routes de lecture équipe/collectif, clôture simulée et présentation d'attentions à l'adaptateur transactionnel. Aucun tenant, UID ou équipe choisi librement par le navigateur : la portée provient du profil fictif serveur, puis les affectations sont contrôlées dans Firestore.
- `scripts/serve-firebase.mjs` démarre ce mode distinct. `src/server/http.mjs` réutilise le serveur statique et les contrôles d'origine/corps ; le mode Firebase n'a aucun repli vers les fichiers de démonstration.
- `web/connexion.html` et `src/web/login.ts` proposent deux comptes fictifs (Lex EKHO et Atelier). Leur connexion utilise réellement Auth Emulator côté serveur. C'est un sélecteur de démonstration, pas une invitation ni une authentification personnelle de salarié.
- Cookie opaque HttpOnly, SameSite strict, Secure lorsque l'origine est HTTPS. Session serveur en mémoire pendant 55 minutes ; jeton Firebase uniquement côté serveur, aucun stockage navigateur de ce jeton. Toutes les lectures métier le revérifient. Écritures protégées par origine et CSRF. Connexion renouvelle le cookie ; déconnexion supprime la session serveur. Aucun jeton dans les réponses ou logs applicatifs.
- `demo-client.ts` conserve les cartes et redirige vers la connexion en cas de refus 401/403. Déconnexion visible dans l'en-tête sans ajouter une cinquième entrée au menu mobile. Les attentions, la progression, les bornes et la réception reprennent les modules existants.
- Les deux campagnes fictives sont créées uniquement si absentes. Une reconnexion conserve donc leur progression tant que les émulateurs gardent leurs données. Les participants qui choisissent le même compte fictif partagent sa campagne ; cela ne représente pas l'identité personnelle des futurs collaborateurs.

## Recette

Local : `npm run typecheck`, `npm run build:web`, `npm run test:visual` (16), `npm run test:events` (12) réussis. Avec Java 21 : `npm run test:firebase` réussit, **3 tests**, dont un scénario HTTP intégré supplémentaire : accès sans session, origine étrangère, champs de portée interdits, cookie, CSRF, répétition, refresh, collectif, autre entreprise, logout effectif et reconnexion conservant la distance. Les scénarios V3-D2 de concurrence/règles/retrait de droits restent inclus.

`playwright.firebase.config.mjs` et `tests/firebase-browser/login.spec.mjs` ajoutent un parcours complet à 1440×900 et 390×844. Le workflow Firebase construit la sortie publique, démarre les émulateurs, exécute la recette HTTP et navigateur, puis conserve les captures. Résultat et références CI à consigner après exécution.

La tentative de prévisualisation manuelle a rencontré des limites de son environnement Java (chemin temporaire non partagé, puis bibliothèque `libjli.so` introuvable). Aucun test navigateur local déclaré réussi. La configuration temporaire de lancement a été retirée de `package.json` ; la recette navigateur utilise la CI équipée de Java 21.

## Limites et suite

Aucun accès réel ni mot de passe utilisateur. Comptes, mots de passe et chiffres exclusivement fictifs. Le mode impose les deux hôtes locaux et le projet `demo-rc-voyage`. Aucune invitation envoyée, pas de récupération de compte, pas de renouvellement de jeton : après expiration ou redémarrage serveur, reconnexion nécessaire. Après arrêt des émulateurs sans export, leurs données sont perdues ; aucune sauvegarde de production revendiquée. Pas de staging, publication ou fusion sur main.

Les futures invitations personnelles et l'onboarding collaborateur doivent remplacer ce sélecteur fictif avant toute utilisation réelle. Puis restent le vote d'équipe, les préférences privées, trois questions hebdomadaires et le cockpit. Les règles métier, confidentialité individuelle et critères de recette du CDC V3 continuent de s'appliquer. Aucun test d'authentification de production ni audit complet d'accessibilité dans cette tranche.
